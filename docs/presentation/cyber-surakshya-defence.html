Cyber SurakshyaDetection was never the hard part.

A multi-agent intrusion detection and response platform that classifies network flows, explains what it found, decides what to do, and then refuses to do it without an analyst.

CandidateSurya Pokhrel
DatasetCICIDS2017 · 2,520,751 flows
Served modelMLP · macro F1 0.966
Codebase29,353 LOC · 446 tests
Open with the subtitle. Most IDS projects stop at a confusion matrix. Mine argues that the interesting engineering starts after the classifier is good — in what the system does with a detection, and in what it refuses to do automatically. Two defensible findings tonight: a metric selection trap that would have shipped a broken model, and a response layer designed around refusal.
The problem

A detection nobody acts on is
not a defence

  • Signature-based IDS cannot generalise to attack variants; they match what has already been seen.
  • ML-based IDS generalise, but stop at a label. Somebody still has to read it, judge it, and act.
  • SOC teams face alert fatigue — the bottleneck has moved from detecting to triaging and responding.
  • Fully automated response is the obvious answer and the dangerous one: an automated block on a false positive is a self-inflicted denial of service.
The gap this project addresses

Published network-IDS work is dominated by classifier benchmarking on CICIDS2017. The pipeline after the classifier — triage, decision, authorisation, containment, feedback — is largely left as an implementation detail.

Position

Treat the IDS as one component inside an agentic operations platform, and make the authorisation boundary an explicit, testable part of the architecture rather than an afterthought.

Keep this short — two minutes maximum. The examiner's question here is usually "why multi-agent, why not just a bigger model". Answer: because the remaining problems are not classification problems. Triage, authorisation and feedback are workflow problems, and a single model cannot express "I am confident but not permitted".
Research questions

Three questions this work answers

RQ 1 — evaluation

On a dataset this imbalanced, does the standard reporting metric select the right model?

CICIDS2017 is ~99% four classes. Accuracy and weighted F1 are the conventional headline figures. Do they distinguish a model that detects every attack family from one blind to the rarest?

RQ 2 — architecture

Can a supervised classifier and an unsupervised anomaly layer be combined so that novel traffic is not silently dismissed as benign?

A closed-set classifier must assign one of seven labels. What happens to traffic that belongs to none of them?

RQ 3 — autonomy

How much of the response can be automated without removing the analyst from the loop?

Where exactly is the boundary between what the system may do on its own and what requires a human ruling — and can that boundary be enforced rather than documented?

Say these are the three questions and that the rest of the talk answers them in order. If time is cut short, RQ1 is the one with the strongest empirical result — go there first.

The structural fact

The four largest classes are 99.5% of all flows. The two most interesting attack families — web application attacks and botnet C2 — are 0.17% between them.

Consequence

A model that ignores both rare classes entirely still reports ~99% accuracy. Any metric weighted by support inherits that blindness.

Two decisions worth defending

Scaler fitted on the training split only. Fitting on the full dataset leaks test-set distribution into the transform and inflates every reported figure.

Balancing applied after the split, to the training set only. The test set keeps the real class distribution, so the reported recall on WEBATTACK is recall on genuinely rare traffic.

Why hybrid, not SMOTE

BENIGN is capped rather than discarded; rare classes are oversampled to a floor. Implemented directly — no external imbalance library — so the procedure is reproducible from the repository alone and the random seed fully determines the result.

Feature set

Top-40 by ANOVA F-score, plus features required to translate Zeek conn.log telemetry — 42 columns, fixed and recorded in feature_columns.json.

The leakage point is the one an examiner will probe. Be ready to say exactly where StandardScaler.fit is called — after train_test_split, on X_train only — and that balance_classes runs after that, on the training partition.
Models

Six models, two jobs

Supervised — which of seven classes

Random Forest

300 trees, full depth, max_features="sqrt", balanced class weights. Bagging supplies the regularisation.

Histogram Gradient Boosting

300 rounds, depth 8, lr 0.05, L2 = 1.0, early stopping. Histogram-binned for ~10× the speed of classic GB at equal accuracy.

Deep Neural Network — MLP

512 → 256 → 128, ReLU, Adam, early stopping. L2 alpha substitutes for dropout; upstream StandardScaler substitutes for batch norm.

Voting Ensemble

Soft vote over the three above — averages probability vectors, not hard votes.

Unsupervised — is this traffic familiar

Isolation Forest

200 trees, fitted on BENIGN rows only. Threshold calibrated at the 5th percentile of benign anomaly scores rather than left at the contamination default.

Autoencoder

d → 2e → e → 2e → d, ReLU, MSE, mini-batch SGD with gradient clipping. Implemented in NumPy with manual backpropagation — no TensorFlow or PyTorch dependency. Threshold at the 99th percentile of benign reconstruction error.

Why train on benign only

Both learn the shape of normal traffic. They therefore answer a question the classifier structurally cannot: have I seen traffic like this before — which is defined for attacks that were never in the training set.

If asked why the autoencoder is hand-written: it removes a 2GB dependency from a project whose whole point is reproducibility, and manual backprop is defensible in a final-year submission. Concede readily that a Keras autoencoder would train faster and probably converge lower — it is listed in future work.

The fix

Selection as an enforced rule, not a judgement call

Before

max(all_metrics, key=f1_weighted) — one line, and it would happily promote a model with 0.10 recall on web attacks.

After

Rank by macro F1, but only among models clearing a 50% recall floor on every single class. Models below the floor are named and excluded in the training log.

If no model clears the floor, the best macro F1 is still served — refusing to save anything would leave the platform with no detector — but the log says so loudly.

Recorded, not assumed

manifest.json names the served artifact, the rule that chose it, the dataset fingerprint, the seed and the library versions. Which model is in production is an auditable fact.

Why this is a contribution, not a bug fix

The trap is a property of the dataset, not of my code. Any CICIDS2017 study reporting accuracy or weighted F1 as its headline is exposed to it. Three of my four models score above 0.99 weighted F1 while being effectively blind to web attacks — and published work using those same metrics on this same dataset cannot distinguish those cases either.

Expected challenge: "isn't the floor arbitrary at 50%?" Yes, and say so — it is a policy parameter, not a discovered constant. Defend it as: any value in a broad middle range separates the observed cases, because the rejected models sit at 0.08-0.10 and the accepted one at 0.74. The result is not sensitive to the exact threshold anywhere between roughly 0.2 and 0.7.
RQ 2 · the closed-set problem

A classifier cannot say "I have never seen this"

  • The seven-class model must assign one of seven labels. Traffic belonging to none of them is forced into the nearest — usually BENIGN.
  • Two detectors trained on benign traffic only supply the second opinion, combined through an OR gate: either firing raises the flag.
  • When the classifier says BENIGN and the anomaly layer disagrees, the detection is downgraded to INCONCLUSIVE and surfaced — not dismissed.
  • Both detectors ship with thresholds calibrated on benign percentiles and persisted alongside the models.
Why two and not one

They fail differently. Isolation Forest finds points that isolate in few random splits — global statistical outliers. The autoencoder finds flows it cannot reconstruct — structural unfamiliarity. A flow can be ordinary in every marginal distribution and still be structurally novel.

Cost, stated plainly

An OR gate maximises recall and pays for it in false positives. That is the correct trade only because the output is INCONCLUSIVE — a triage signal — and not an automated block. The authorisation layer is what makes this affordable.

The link between this slide and the next is the argument of the whole thesis: an aggressive detector is only safe because the response layer is conservative. If asked for anomaly-layer numbers, they are in the training log per detector and combined — quote them from the backup slide rather than from memory.

Hub and spoke, not a chain

Every worker returns to the coordinator, which re-derives outstanding work from state and dispatches the next stage. A linear chain processed exactly one event per run and silently dropped the rest, because each agent handles one pending item per call.

Append-only shared state

LangGraph operator.add reducers. Nodes return only their additions; no node can mutate another's output. Every result is validated by Pydantic v2 with extra="forbid".

Live-lock is a designed-for failure

Agents catch their own exceptions and return without producing a result — so "route while work is pending" would dispatch to a broken stage forever. The coordinator compares output-list lengths across dispatches, excludes any stage that made no progress, and records why as a run anomaly.

Learning sits outside the loop

Deliberately not a pipeline node — as one it would re-derive platform-wide metrics on every single flow.

Likely question: "isn't this over-engineered for a student project?" The stall detector exists because the live-lock actually happened during development. Say that — a mechanism introduced in response to an observed failure is easier to defend than one introduced on principle.

  • Four independent gates. Each refusal is recorded as a result — verdict, the rule that fired, and the reason — never as a silent no-op.
  • Verdicts are ALLOW, DOWNGRADE, REQUIRE_APPROVAL, DENY. A downgrade executes a weaker action rather than the requested one.
  • Awaiting-approval is resumable, not terminal: the coordinator retries it once an analyst rules.
The invariant that matters

The decision engine cannot approve itself. A decision setting requires_approval=False clears the decision-level gate, but never substitutes for a human where the trust policy demands one. The live approval store is consulted first, and an engine's own trust tier is what determines whether its judgement is sufficient.

Fail-closed by default

Policy loads from config/response_policy.yaml, falling back to fail-closed defaults if absent. An unreadable policy file denies; it does not permit.

This is finding two and the answer to RQ3. The boundary is enforced in code and covered by tests, not described in a document. If challenged on "why not just trust a confident model" — point back to the ensemble at 0.9926 weighted F1 with 10% web-attack recall. Confidence is not the same as correctness, and the system is built on that assumption.

Why a stream in the middle

Capture and analysis fail independently and run at different rates. The stream decouples them, and each side authenticates as its own Redis ACL user — the capture side cannot read the pipeline's keyspace.

A second telemetry path

Zeek conn.log fields are translated directly into CICIDS2017 features, so the platform interoperates with an existing sensor without running its own capture.

Capture is never a side effect of booting

The ingestion service is constructed at startup and deliberately not started. Beginning a packet capture is a privileged act that must be an explicit operator decision via POST /ingestion/start.

Known limitation

Inter-arrival-time statistics and TCP window features are unavailable from a default Zeek conn.log and are zero-filled on that path. The capture path via CICFlowMeter computes them properly.

If asked whether it has been tested on live traffic: yes, on a local interface, and the honest caveat is that a lab network is not a production network. The domain shift question belongs on the limitations slide — do not pre-empt it here.
Closing the loop

The system cannot grade its own homework

  • A platform has no way to detect its own false positives by introspection — a confident wrong answer looks exactly like a confident right one.
  • Analyst feedback via POST /learning/feedback is therefore the highest-value input the system takes, and the only ground truth it ever receives after deployment.
  • The LearningAgent joins detections to feedback, computes precision, recall and false-positive rate over a time window, discovers recurring patterns, and produces ranked recommendations.
  • It recommends without executing. Automated retraining is deliberately out of scope — the agent proposes, a human runs train.py.
Why automated retraining was excluded

A feedback loop that retrains itself on its own outputs will drift, and drift in a security control is a silent failure. Nothing in this project measures that drift, so building the loop would have been irresponsible rather than ambitious.

What is persisted

Every detection, analysis, decision, response, approval and feedback record is written to a Qdrant + SQLite memory provider, so the learning window spans restarts.

"Recommends without executing" is a design position, not a missing feature — present it that way. The strongest version of the argument: I can build the loop, but I cannot yet measure whether it is helping, so shipping it would be shipping an unmeasurable control.

Reproducibility

manifest.json records the dataset fingerprint, row cap, random seed, feature count, and the scikit-learn / NumPy / joblib versions the artifacts were pickled under — because a pickle that will not unpickle is not a result.

Validation at the boundaries

Pydantic v2 with extra="forbid" throughout. Cross-field validators enforce the invariants: a BENIGN detection cannot carry is_anomaly=True; severity must match the numeric risk band.

Tested where it matters

The response authorisation path — trust tiers, protected targets, approval resumption, idempotency — carries the densest test coverage in the project, because it is the only layer that acts on anything outside the process.

What is not validated

There is no benchmark against a second dataset, and no adversarial evaluation. Both are named in future work rather than glossed over.

Do not oversell the test count — an examiner may ask what they cover. The honest summary: unit coverage across every layer, integration coverage of the graph and the response gates, and no end-to-end test that drives the FastAPI layer through a live capture. Say that before being asked.
Threats to validity

What this work does not establish

External validity

One dataset, one network

CICIDS2017 is a controlled 2017 capture. Nothing here demonstrates generalisation to a modern production network, and the domain shift is likely severe.

Coverage

Seven classes, no infiltration

The cleaned dataset has zero infiltration rows. Lateral movement and insider activity are undetectable by this model, not merely detected poorly.

Adversarial

No evasion evaluation

The model has not been tested against adversarial perturbation or deliberate feature manipulation. A flow-statistics classifier is a plausible target for both.

Rare classes

BOTNET recall 0.74

The served model's weakest class. Roughly one in four botnet C2 flows is missed — reported, not smoothed over.

Response

Simulated executors only

The authorisation architecture is complete and tested; no real containment has been performed against real infrastructure.

Learning

Feedback-dependent

The learning metrics are only as good as the analyst labels they consume. With no feedback, the LearningAgent reports nothing meaningful.

Backup slide
Anticipated question

"Why did the DNN beat the ensemble? Ensembles usually win."

The mechanism

Soft voting averages probability vectors. Two of the three base estimators — Random Forest and Gradient Boosting — are near-blind on WEBATTACK, assigning it very low probability. Averaging three vectors where two are confidently wrong drags the correct one down.

The evidence

The ensemble's WEBATTACK recall is 0.100 — between GB's 0.096 and RF's 0.077, and nowhere near the DNN's 0.953. It inherited the majority's blindness rather than the minority's sight.

The general lesson

Ensembling helps when base learners fail independently. Here RF and HistGB are both axis-aligned tree models trained on the same features and they fail the same way on the same rare class. The ensemble had no diversity to exploit on exactly the classes that mattered.

What I would do differently

Weight the vote by per-class competence rather than averaging uniformly, or drop base learners that fail the recall floor before ensembling at all. Both are straightforward; neither was needed once the DNN cleared the floor on its own.

This is the most likely technical question in the whole defence. The independence argument is the real answer — have it ready in one sentence: ensembles need base learners that fail differently, and mine failed identically on the rare classes.
Backup slide
Anticipated question

"Isn't 99.7% accuracy just overfitting to CICIDS2017?"

What rules out simple overfitting

The 20% test split is stratified and held out before scaling and balancing. The scaler is fitted on training rows only. The MLP uses early stopping on a further 10% internal validation split, so training stops before it memorises.

What the number actually means

99.7% accuracy is unremarkable here and I do not lead with it — a model predicting only the four majority classes reaches ~99%. The defensible figure is macro F1 0.966, which no trivial strategy achieves.

What I cannot rule out

Dataset overfitting is a real and unaddressed risk. CICIDS2017 was generated in a controlled testbed with scripted attacks. High in-distribution performance says little about a production network in 2026.

This is exactly why cross-dataset evaluation is the first item in future work. I would not deploy this model on a live network on the strength of these numbers alone.

Distinguish the two senses of overfitting explicitly — overfitting the training split, which the methodology rules out, and overfitting the dataset, which it does not. Conceding the second cleanly is what makes the first credible.
Backup slide
Anticipated question

"Why LangGraph? Couldn't this be plain functions?"

Honest answer first

Yes. Four sequential function calls would produce the same detection for a single event. For the linear case LangGraph buys very little, and I would not defend it on that case alone.

What it buys once routing is conditional

The pipeline is not linear: a run carries N events at mixed stages, responses awaiting approval must be resumed later, and stalled stages must be excluded mid-run. That is a state machine with conditional edges, and expressing it as nested loops over mutable lists is where the bugs live.

The concrete benefits taken

Append-only reducers — no node can corrupt another's output.
Conditional edges — routing policy is one pure, unit-testable function with no graph, no mocks.
State validation — the whole run state is one Pydantic model, checked on entry and exit.

The cost

A dependency, a recursion limit to tune, and a graph that must be compiled before it can be executed. It is a real trade, not a free win.

Opening with "yes, you could" disarms the question. The routing function being pure and testable without a graph is the strongest concrete point — it is the thing that would be hardest to keep clean in hand-rolled control flow.
Backup slide
Anticipated question

"How is the demo not just replaying hard-coded attacks?"

It used to be — and that was a defect

An earlier version carried six hand-written attack dictionaries. Each supplied between 16 and 55 feature names against a model needing 42 specific ones, so every profile was partly zero-filled before it reached the classifier, and several supplied features the model does not use at all.

The demo was scoring fabricated vectors — the exact failure the strict flow normaliser exists to prevent.

What it does now

A separate script streams the labelled dataset and computes a per-class median over up to 50,000 real flows per class, covering all 42 features with no guessing about what a port scan "looks like" numerically.

Median, not mean: these features are heavily skewed — Flow Bytes/s spans zero to 1e9 — so a mean lands on a value no real flow ever takes. A median is an actual point in the class.

Fail loudly

If the profile artifact is missing, the endpoint returns 503 rather than falling back to fabricated vectors. Only the source IP is synthetic.

Volunteering that this was previously wrong is a strength, not a risk — it shows the artifacts were audited rather than trusted, and the median-versus-mean reasoning demonstrates you understand the feature distributions rather than just the API.
